# S7 负载感知线程分配策略设计（只设计，不默认启用）

状态：研究稿，未进入正式功能，未在真机做 A/B。
适用范围：AppOptR 2.3.0 之后的静态规则体系。
产出：本文档 + 后续可选的实验分支实现。默认配置下运行时行为与 2.3.0 完全一致。

---

## 1. 目标与非目标

目标：在“规则决定可用 CPU 集合”的前提下，允许同一条规则映射到多个簇时，由低频负载信息在
**集合内部**决定当前落在哪个簇，减少大核争抢与小核闲置同时发生的概率。

非目标（明确禁止）：

- 不改变规则语义，不扩大线程被允许使用的 CPU 集合。
- 不读取 `scaling_cur_freq` 作为调度依据，不写 `scaling_governor`，不调频、不改 sched 参数、不碰 GPU DVFS。
- 不做 FPS 高频采样，不常驻 Perfetto，不做高频 `/proc` 扫描。
- 不引入常驻后台监控线程；采样必须依附于主循环且只在被管理应用活跃时进行。

判定原则：收益无法在真机 A/B 中稳定复现时，保持默认关闭。

## 2. 现有基础（2.3.0 已具备的能力）

| 能力 | 位置 | 对 S7 的作用 |
|------|------|--------------|
| 包内规则索引 `rule_index: HashMap<String, PkgRules>` | `config.rs` / `rule_match.rs` | L1 显式规则的 O(1) 查询入口 |
| 逐包规则指纹 `pkg_sig` + 增量重建 `config_rescan` | `config.rs` / `ebpf_mode.rs` | 策略参数变更时只重建受影响包 |
| 语义簇 `e_core/p_core/hp_core` 与降级标记 `topo_degraded`、依据 `topo_source` | `cpuset.rs` | 策略只在“确实存在多簇”时才有意义 |
| 就绪目录缓存 `READY_DIRS` 与执行层建目录 | `apply_affinity.rs` | 动态迁移可复用既定 cpuset 目录，不重复建目录 |
| 线程缓存 `ProcCache`（tid → pid/pkg/cpus/cpuset_dir） | `cache.rs` | 角色与迁移状态可挂在同一结构上 |
| 事件驱动 RENAME/EXEC/EXIT + 60 秒丢弃对账 | `ebpf_mode.rs` | 线程身份变化的触发源 |
| Proc 模式 PID 差分 + 新线程增量发现 | `proc_mode.rs` | 无 eBPF 设备上的等价触发源 |

因此 L3“父线程角色继承”在默认内核态下拿不到父线程角色，需要按下文 §6.1 的方式按需恢复。

## 3. 线程角色识别（L1–L4）

角色只是策略输入，**不直接等价于某个簇**。

```rust
enum Role { Critical, Latency, Worker, Background, Unknown }
```

| 层级 | 依据 | 实现位置 | 备注 |
|------|------|----------|------|
| L1 | 显式规则（线程规则命中） | `rule_match::thread_affinity` | 已存在，优先级最高 |
| L2 | 已知线程角色模式表 | 新增 `roles.rs`（≤120 行） | 仅做静态字符串匹配，不引入正则依赖 |
| L3 | 父线程角色继承（FORK） | 需恢复 FORK 事件，见 §6.1 | 未启用时退化为 L4 |
| L4 | 包级规则 / 未命中兜底 | `thread_affinity` 的 `unmatched` 分支 | `keep` 语义下不干预 |

L2 初始模式表（只收公开、稳定的命名习惯，允许整表关闭）：

| 模式（`fnmatch`） | 角色 | 依据 |
|------------------|------|------|
| `RenderThread` | Critical | Android UI 渲染线程 |
| `hwuiTask*` | Worker | HWUI 线程池 |
| `UnityGfx*`、`GfxDeviceWorker` | Latency | Unity 渲染提交 |
| `RHIThread`、`RHIT` | Latency | UE 渲染硬件接口线程 |
| `GameThread` | Critical | UE 逻辑主线程 |
| `TaskGraph*` | Worker | UE 任务图 |
| `AudioTrack`、`AudioOut*` | Critical | 音频输出，抖动敏感 |
| `*.io`、`DefaultDispatcher*`、`OkHttp*`、`pool-*` | Background | 常见 IO/协程池命名 |

规则：L2 命中只影响“角色标签”，不影响允许集合；允许集合始终来自 L1/L4 的规则。

## 4. 负载评估

### 4.1 数据源

只读 `/proc/stat` 的 `cpuN` 行，按簇求和后做增量：

```
busy  = user + nice + system + irq + softirq + steal
total = busy + idle + iowait
利用率 = Δbusy / Δtotal
```

- 采样粒度 1 秒，由主循环既有节奏派生，不新增线程。
- 只在被管理应用“活跃”时采样，见 §4.2；不活跃时计数清零，恢复时重新取基线，避免跨时段差分。
- 单次采样成本：一次 `read` + 数十行解析，约 10–20 µs，可忽略。

### 4.2 活跃判定（不依赖 Android 框架）

```
活跃 = 被管理进程存在，且 (utime+stime) 在最近 1 秒内有增长
```

`/proc/<pid>/stat` 的 utime/stime 已在 Proc 模式扫描范围内，eBPF 模式下只需对缓存中的 pid 读一次。
明确不使用 `dumpsys`、`am`、`ActivityManager` 等重接口，也不做前后台判定的额外轮询。

### 4.3 禁止项

- 不读 `scaling_cur_freq`：其读数受采样窗口与 governor 影响，不能代表真实算力。
- 不采样进程级 CPU 占比作为决策依据（`/proc/<pid>/stat` 仅用于活跃判定）。

## 5. 迁移策略与防抖

### 5.1 允许集合

规则表给出允许集合 `allowed`（可能是 `p-core,hp-core` 这样的并集）。
负载信息只能把线程从 `allowed` 中的一个子集迁到 `allowed` 内的另一个子集，**永不超过 `allowed`**。
未配置规则的线程在 `keep` 语义下不参与迁移。

### 5.2 参数（实验初始值，非最终值）

| 参数 | 初始值 | 说明 |
|------|--------|------|
| 采样周期 | 1 s | 与主循环同源 |
| 最小驻留时间 | 5 s | 新线程先跑完冷启动，再参与判定 |
| 连续确认次数 | 3 | 连续 3 次采样同向才动作 |
| 迁移阈值 | 目标簇负载差 > 15% | 低于阈值不动 |
| 同线程迁移冷却 | 10 s | 防止高频重试 |
| 反向冷却 | 90 s | 刚迁出的簇不得马上迁回，掐掉 p ↔ hp 乒乓 |
| 单轮迁移上限 | 1 个线程 | 跨簇迁移必然丢缓存，一次只动一个 |
| 目标簇配额 | 单核簇 1、多核簇 2×核数 | 防止多个 Worker 挤进超大核 |
| 线程迁移预算 | 180 s 内 3 次 | 超限即冻结该线程，直到退出或规则重扫 |

### 5.3 状态机（每线程）

```
Idle --(负载差达标 x3)--> Candidate --(驻留>=5s、冷却已过、非回弹)--> Migrating --> Idle
   ^                                                                        |
   +------------------(负载回落 / 迁移失败 ESRCH / 预算耗尽冻结)-------------+
```

判定顺序：允许集合 → 角色约束（Critical 至少保留 hp 可用性）→ 阈值 → 驻留 → 冷却 →
反向冷却 → 目标簇配额 → 单线程预算。

### 5.4 执行方式

- 只调用 `sched_setaffinity`，**不改 cpuset 目录**。cpuset 是静态集合，动态改 `tasks` 会带来
  cgroup 级的额外抖动与不可预期的继承行为。
- 迁移后更新 `ProcCache` 中的 `cpus`，让既有的 `affinity_sync` 与 `getaffinity` 短路继续生效。
- 失败（ESRCH）按线程退出处理，不重试。

## 6. 需要新增的内核态/事件支持

### 6.1 L3 父线程角色继承（可选，按需恢复）

S3 移除 FORK 事件后，内核只知道“子 tid 已被管理”，不知道父线程角色。恢复方式二选一：

1. **按需 attach**：新增独立 tracepoint 程序 `sched_process_fork_role`，仅在 `@sched` 启用时加载，
   事件里带 `parent_tid`；默认配置不加载，不影响 2.3.0 事件量。
2. **用户态推断**：RENAME 时读 `/proc/<tid>/status` 的 `Tgid`，按“主线程角色 = 包级角色”推断，
   放弃细粒度继承。成本高、精度低，仅作降级方案。

推荐方案 1，且必须满足：Map 结构与现有 `ProcEvent` 分离（新增事件类型 5），旧用户态读到未知类型直接忽略。

### 6.2 ABI 约束

- 不复用 `EVENT_FORK=1` 的编号语义，避免新旧二进制混跑时误解。
- 新增 Map 一律 `Array<u64>` 计数型，读写都在主循环内完成，不做高频轮询。

## 7. 配置与可观测性

建议配置指令（与 `@unmatched` 同级，加载阶段解析）：

```
@sched=off          # 默认，完全关闭
@sched=shadow       # 只计算并记录决策，不执行迁移（推荐的第一阶段）
@sched=on           # 执行迁移，仍受全部约束
```

- `shadow` 模式必须能在 Web 状态页看到“本可迁移但未迁移”的次数与最近决策样本（环形缓冲 ≤32 条）。
- 任何解析失败回退 `off`，不影响静态规则。

### 7.1 诊断（2.3.5 起）

问题定位过去只有「迁移成功」一行日志，失败与跳过全是静默的。现在分四层：

| 层 | 内容 | 去处 |
|----|------|------|
| 绑核计数 | 调用 / 真写 / 短路 / 失败，errno 按 EPERM、EINVAL、ENOSYS 分桶 | 日志摘要（60 s）、Web 诊断 |
| 绑核明细 | `绑核失败: Thread-7(1234) → 4-6（EINVAL：目标集合非法…）` | 日志，同 errno 5 s 一条 |
| S7 决策 | 迁移（含来源簇与前后负载）、失败、回弹被拦、预算冻结 | 日志 + 事件环 |
| 跳过原因 | 允许集合不足 / 角色 / 无更空目标 / 驻留 / 冷却 / 配额 | Web 诊断，按原因计数 |
| 卡顿信号 | Critical 线程 `schedstat` 就绪等待均值 > 4 ms | 日志（30 s 一条）+ Web 诊断 |

线程表同时给出「期望集合 / 内核实际集合」，未绑住的线程排在最前，直接回答
「这个线程为什么没绑上」。

### 7.2 归因（2.3.6 起）

2.3.5 的日志能回答「失败了多少次」，但回答不了「谁改的、为什么改了也没用」。真机上出现的
`cpuset 写入 EINVAL` + `每 60 秒几百个线程被外部改写` 就是这种情况。2.3.6 补四件事：

| 能力 | 输出 | 用途 |
|------|------|------|
| 时间戳 | 行首 `[+123.4s]`（启动后耗时） | 与掉帧时刻、操作时刻对齐 |
| 漂移归因 | `漂移: X(tid) 期望 4-6 实际 0-7 cpuset=/top-app`，按裁剪/重置/挪簇计数 | 区分 cpuset 限制、热插拔重置、被挪簇 |
| 写后回读 | 返回 0 后再读一次，仍不一致记 `无效绑定` 并停绑 300 s | 掐掉「写→被裁→再写」死循环 |
| cpuset 现场 | 目标/父/根三层 `cpus`、`effective_cpus` 与线程 cpuset | 判断目录没建成、父级无交集、线程在别组 |

配套两道闸：

- **cpuset 熔断**：连续 3 次失败暂停 120 秒，到期半开尝试一次。失败路径上的 open/write
  在调度紧张时同样是负担。
- **无效绑定退避**：`applied` 标记区分「还没绑上」与「绑了被改回去」，后者才计入漂移；
  写入返回成功但回读仍不一致的线程，300 秒内不再重绑。

S7 侧新增周期摘要，开关为 `on` 时每 60 秒一行：

```
[+180.0s] S7: 近 60 秒 60 轮、探测 3840 线程、迁移 0 次（累计 0），回弹 0、冻结 0，
          簇负载 120/640/310‰，状态 运行中；跳过：允许集合 3021 / 角色 719 / 负载未达标 100
```

`shadow` 档报「本可迁移」；`levels < 2`、无活跃进程等不推进的情况直接报状态，
避免「开关开了但什么都没发生」无从解释。若整周期跳过全是「允许集合不足两层」，
摘要会追加一句：规则只覆盖一个簇，S7 没有可让位的目标，需写成跨簇（如 `all-core`）才会生效。

### 7.3 系统 cpuset 分组（2.3.7 起）

真机 2.3.6 的日志把「绑不住」指向了系统侧，而不是绑定逻辑：

```
cpuset 现场: 线程 19946 所在组 /AppOpt/4-6(4-6，AppOpt组) 与目标有交集
漂移: process reaper(29948) 期望 4-6 实际 0-3 cpuset=/background
漂移: Thread-232(19509) 期望 4-6 实际 4-5 cpuset=/foreground
```

内核在两种时机把组内线程的亲和性收敛到该组的 `effective_cpus`：

1. 线程被写进某个 cgroup（`cpuset_attach` 直接 `set_cpus_allowed_ptr`）；
2. 组自身的 `cpuset.cpus` 被改动（Android 会随前后台切换、热插拔重配）。

所以只要线程不在 AppOpt 自己的组里，任何 `sched_setaffinity` 都会被下一次收敛覆盖；
当目标核根本不在所在组的 `effective_cpus` 内时，内核连写都不让写：

- 写 `cgroup.procs` → `cpuset_can_attach` 判定交集为空，返回 `EINVAL`；
- `sched_setaffinity` → 同样是交集为空，返回 `EINVAL`。

两条路同时堵死，线程就永远停在系统给它的小核上。

2.3.7 的应对：

| 手段 | 做法 | 代价 |
|------|------|------|
| 两步迁组 | 先写 base（全核，必然成功），抬出原组后再写目标组 | 毫秒级窗口内亲和性先变全核 |
| 尊重后台组（默认） | 线程在 `background`/`system-background`/`restricted` 且目标不在组内时跳过 | 后台线程仍跑小核，符合系统意图 |
| 强制接管 | `@sysgroup=takeover`，等同关闭上一条 | 后台线程上大核，耗电与发热上升 |

配置行：

```conf
@sysgroup=respect    # 默认，尊重系统分组
@sysgroup=takeover   # 强制把线程拉进 AppOpt 组
```

切前台时系统会把线程移出 `background`，`affinity_sync` 会重新评估并恢复绑定，
不需要重启。

### 7.4 生效集合必须自己算（2.3.8 起）

2.3.7 在真机上的日志里，`cpuset` 现场三行的 `effective` 全是 `-`：

```
cpuset 现场: 目标[/dev/cpuset/AppOpt/4-6] cpus=4-6 mems=0 effective=-
cpuset 现场: 线程 6405 所在组 /AppOpt(-，AppOpt组) 可达性未知（读不到生效集合）
```

部分 Android 内核不导出 `cpuset.effective_cpus` / `cpuset.cpus.effective`。2.3.7
的实现是「读不到就不做判断」，于是「尊重系统分组」一次都没触发，
`/background`(0-3) 的线程照样被硬写 4-6，`+2599s` 之后每分钟 495 次 EINVAL。

生效集合的定义就是「自身 `cpus` 与所有祖先 `cpus` 的交集」，所以读不到导出值
时按定义算即可：

| 层级 | 读什么 | 空值含义 |
|------|--------|----------|
| v1 | `<dir>/cpus` | 本组不能运行任何任务 |
| v2 | `<dir>/cpuset.cpus` | 继承父级，跳过这一层 |

两个补充：

- **组归属每轮重算**。`blocked` 只在首次见到线程时算一次是不够的——应用切后台时
  系统会把它从 `top-app` 搬进 `background`，此时必须重新判定，否则每轮硬写一次。
  代价是每 60 秒每个受管线程读一次 `/proc/<tid>/cgroup`，远小于几百次失败的
  `sched_setaffinity`。
- **失败与漂移分开计数**。目标与所在组无交集时归入「不可达」，不再同时记成
  「挪簇」。真机日志里 `挪簇 495` 就是 495 次失败，看着像线程被搬了 495 次。

### 7.5 单簇规则下 S7 的代价（2.3.8 起）

规则全部只覆盖一个簇时，S7 的「让位」前提不成立，每轮判定必然全部跳过。
但采样开销仍然发生：每秒一轮、每轮最多 64 个线程的 `/proc/stat` +
`schedstat` + `comm`。真机日志里 `近 60 秒 56 轮、探测 3584 线程、迁移 0 次`
持续了 40 分钟，这份开销本身就是掉帧来源之一。

2.3.8 起，连续 5 轮「探到线程、零迁移、跳过全是允许集合不足」后，判定间隔
从 1 秒降到 8 秒，状态显示为「规则单簇，判定已降频」；出现任何一次真实迁移
或规则改动立刻恢复每秒判定。

### 7.6 cgroup 写入口径（2.3.9 起）

2.3.8 的日志里 `cpuset: 自检失败，写入失败（Invalid argument (os error 22)）`
看着像设备限制，实际是写入方式的问题：`writeln!` 会被拆成两次 `write`，
第二段只有 `"\n"`，内核 `strstrip` 后是空串，`kstrtoint` 失败返回 `EINVAL`。

```
write(3, "13552", 5) = 5   ← 线程在这一步已经迁进目标组
write(3, "\n",    1) = 1   ← EINVAL，被当成「迁移失败」
```

两个直接后果：

- 迁移成功与迁移被拒在日志里完全一样，都是 EINVAL，「时灵时不灵」就此无解；
- 两步迁组里 base 回退那一步也被误判成「连 base 都写不进去」，把排查方向
  从「目标集合」带到「挂载与权限」。

所以写 `tasks` 必须一次写完、不带分隔符，并且自检要看**回读**：

| 检查 | 判据 | 失败含义 |
|------|------|----------|
| 能否打开 | `open(tasks, O_APPEND)` | 目录没建成、权限、只读挂载 |
| 能否写入 | `write_all(十进制 tid)` | 内核拒绝迁移（交集为空等） |
| 是否迁进 | `/proc/<tid>/cgroup` 等于 base | 写返回 0 但组没变：只读或被裁剪 |

### 7.7 目标要按组的生效集合裁剪（2.3.9 起）

同一次真机日志里还有一类噪音：`182 个线程写入返回成功但回读仍不一致`，
样例全是 `期望 4-6 实际 4-5 cpuset=/foreground`。这台机器的 `/foreground`
只有 `0-5`，`4-6` 写进去被内核求交成 `4-5`，回读不一致 → 判成「写了也白写」
→ 停 300 秒。每 60 秒重来一遍，线程数还越来越多。

现在的处理分三种，取决于「此刻能不能把线程迁进自己的组」：

| 情形 | 绑定集合 | 理由 |
|------|----------|------|
| 组不限制 / 读不到生效集合 | 规则原值 | 读不到不猜 |
| 交集为空 | 跳过（respect）或两步迁组硬抬（takeover） | 写多少遍都是 EINVAL |
| 交集更小且能迁组 | 规则原值 | 迁进 `AppOpt/<集合>` 后组就是目标 |
| 交集更小且不能迁组 | `规则 ∩ 生效集合` | 只有一条腿时，写全集必然被裁 |

裁剪结果不会粘住：`TaskEntry` 同时保留规则原值 `want` 与实际绑定的 `cpus`，
组放开、接管恢复或熔断半开成功之后，下一轮就回到 `want`。
被裁剪时只播报一次（按组去重），不重复刷屏。

---

### 7.8 S7 落点与定期校验的契约（2.3.10 起）

2.3.9 之前，两条路径写的是同一个字段、语义相反：

| 路径 | 写入 | 语义 |
|------|------|------|
| `apply_move_*` | `TaskEntry.cpus = m.cpus` | 这一轮线程实际该在的集合 |
| `affinity_sync` | `TaskEntry.cpus = plan_target(e.want)` | 规则要求的集合 |

`want` 不随迁移改变，所以第二行每 `3 × interval` 秒把第一行覆盖一次。
更糟的是落点只在内存里：proc 模式 60 秒一次 `proc_scan` → `clear()`，
eBPF 模式配置变更 `full_scan` → `clear()`，落点连条目一起消失。

修法是把「谁说了算」写清楚：

- **落点单独存**：`ProcCache.sched: tid → CpuSet`，`clear()` 不清它。
  条目可以重建，落点不能丢。
- **校验只做维持**：`plan_entry()` 先看落点是否仍是规则集合的子集，
  再按组生效集合规划；能维持就维持，不能就丢弃并回到 `want`。
- **三种丢弃条件**：规则改小（越界）、组收紧到落点不可达、S7 被关掉。
  三者都会让落点变成一个内核不接受或不再需要的集合，留着只会制造无效写入。
- **迁移写后回读**：`sched_setaffinity` 返回 0 不代表生效，cgroup 会求交。
  读回与目标不一致就按失败处理，不进落点记录，走 10 秒冷却。

这样 `entry.cpus` 只有一个含义：**这一轮实际该在的集合**。规则值只通过 `want` 参与
「重新规划」，不直接参与「维持现状」。`ThreadState::applied` 与 `entry.cpus` 的比较
也才重新有意义——两者不等只可能是被外部改写，而不是被自己的校验覆盖。

### 7.9 热更新必须叫醒降频（2.4.0 起）

7.5 的降频依据是「连续 30 轮无事可做」，前提是规则不会变。热更新恰好打破这个前提：
`set_mode()` 只在模式变化时清状态，只改规则时模式仍是 `on`，于是 `idle_rounds`
和 `last_decide` 原样保留，新规则最坏要等一个休眠间隔（30 秒）才被看见。

处理方式刻意做得很窄：

```rust
pub fn note_config_change(&mut self) {
    self.idle_rounds = 0;
    self.last_decide = None;
}
```

只清节奏，不清 `threads`。落点、冷却、冻结都还有效，重建整套状态会让刚稳定的线程
重新进入观察期，反而制造抖动。配置变更在 `main` 里调用一次，与 `set_mode` 分开：
后者负责「模式换挡」，前者负责「内容变了」。

## 10. 落地阶段（若立项）

前置（2.3.0 已实现）：解析期统计「允许集合横跨多个核心层」的规则数与包数
（`AppConfig::sched_scope`），写入启动日志并在 Web 设置页展示；拓扑降级时显示「不适用」。
该数字低于规则总数 5% 且涉及包数 < 3 时，下面四个阶段都不必启动——
作用面太小，收益无法覆盖「规则即结果」确定性的损失。

1. **P0 shadow**：角色标签 + 采样 + 决策记录，零迁移。验收：模块 CPU 增幅 < 1%，日志可解释。
2. **P1 受限迁移**：仅 `Worker/Background` 参与，仅允许在 `p-core,hp-core` 集合内迁移。
3. **P2 完整策略**：加入 Critical 约束与单轮配额，进入 A/B。
4. **P3 决策**：A/B 通过才讨论默认值；否则保留 `shadow` 作为诊断工具。

### 10.1 实施状态（2.3.0）

P0 与 P1 已合并，默认 `off`，两者共用同一套状态推进，只用 `own` 区分是否真正写过亲和性。

| 设计项 | 状态 | 落点 |
|---|---|---|
| L1 显式规则 | 沿用 | `rule_match::thread_affinity` |
| L2 模式表 | 已实现 | `roles.rs`，另补 `UnityMain` / `GLThread` / `VkThread` 等 |
| L3 父线程继承 | **未实现（有意）** | 内核 `fork` 已复制 `cpus_mask`，显式继承只会沿线程树放大误判，且不可回滚 |
| L4 包级兜底 | 沿用 | `thread_affinity` 的 `pkg_rules` 分支 |
| 簇负载 | 已实现 | `sched::parse_stat` / `diff_load`，千分比整数比较 |
| 活跃判定 | 已实现 | `sched::pid_ticks`，每轮最多 8 个 pid，按窗口轮转保证全覆盖 |
| 五个防抖参数 | 已实现 | `sched.rs` 顶部常量 |
| 状态机 | 已实现 | `ThreadState { cur, own, applied, streak, .. }` |
| 只改 affinity | 已实现 | `apply_move_*` 只调 `affinity_set`，不写 cpuset 目录 |
| 集合内选择 | 已实现 | `target_cpus` 与允许集合取交集 |
| P1 限定 p/hp | 已实现 | `target_ok` 拒绝 e-core |
| A/B 协议 | 未做 | 只提供 `/api/config` 取数字段，无自动记录脚本 |

设计评审时未写、实现时绕不开的三点：

1. `@sched` 必须进入 `policy_sig`，否则 `on → off` 不会触发重建，已迁移线程停在半 S7 状态。
2. 迁移后必须同步 `TaskEntry.cpus`，否则 `affinity_sync` 每 `3 × interval` 秒按旧集合重设，迁移被拉回。
   2.3.10 起落点另存一份（见 7.8），只同步条目已经不够——条目会被全量重建清掉。
   `cpuset_dir` 保留原值：S7 不改变 cgroup 归属，清空反而会让 `write_task` 落到 base 目录。
3. 判定允许集合必须用 `thread_affinity` 重算，不能用 `entry.cpus`——后者已被上次迁移改写。

`shadow` 与 `on` 的差别有两处：前者推进 `cur` 但不置 `own`（同一线程只计一次 `would`），
且**不产出 `Move`**——迁移在决策层就被截断，不依赖执行层再拦一次；主循环也只在
`@sched=on` 时才接收候选，形成两道独立闸门。`shadow` 全程不碰 cpuset、不调任何
亲和性接口。

后者产出候选 `Move`，但 `cur` / `own` / `applied` / `moved` 要等 `settle` 收到
`AffinityOutcome::Set` 之后才提交。EPERM / EINVAL 只增加 `failed` 并进入冷却，
不会被记成一次成功迁移；ESRCH 则清掉线程状态，避免 tid 复用时继承旧落点。
`own` 为真时，`entry.cpus != applied` 才说明线程被规则重扫拉回，状态随之重置。

## 11. 结论

- 该策略的收益依赖“规则允许集合本身跨簇”这一前提；当前多数用户规则是单簇绑定，收益面有限。
- 主要成本不在 CPU，而在**行为不可解释性**：迁移会让“规则即结果”的确定性消失。
- 因此本次不实现运行时代码、不建长期实验分支；主线只保留本设计文档。
  若后续要做原型，从 `master` 拉 `research/load-aware-placement`，按 §10 的 P0 起步，
  且首个提交只允许包含 `shadow` 模式。
